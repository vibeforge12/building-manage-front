## 1.5 인증 흐름 — 끝까지 추적

### (1) 토큰 저장 위치

**`flutter_secure_storage`** 입니다. `SharedPreferences`가 아닙니다.

`lib/core/network/interceptors/auth_interceptor.dart:12-17`
```dart
static const FlutterSecureStorage _secureStorage = FlutterSecureStorage(
  aOptions: AndroidOptions(encryptedSharedPreferences: true, resetOnError: true),
);
```
키: `access_token`, `refresh_token` (`auth_interceptor.dart:5-6`)

`SharedPreferences`는 다른 용도로만 씁니다: 앱 버전 플래그(`main.dart:89-96`), 승인완료 화면 1회 노출 플래그(`user_login_screen.dart:79-85`, `splash_screen.dart:64-66`).

### (2) 요청에 토큰이 붙는 방법

`auth_interceptor.dart:20-46` — 매 요청마다 SecureStorage를 읽어 `Authorization: Bearer <token>` 헤더를 추가합니다. 단, 아래 공개 엔드포인트는 제외:

```
/auth/resident/register, /auth/manager/register,
/auth/resident/login, /auth/manager/login, /auth/staff/login, /auth/headquarters/login,
/auth/refresh
```

### (3) 로그인 성공 시 토큰 저장 — **경로가 두 개**

- 경로 A: `AuthInterceptor.onResponse` (`auth_interceptor.dart:49-57`) — 응답 path에 `/login`이 포함되고 200이면 자동 저장
- 경로 B: `AuthStateNotifier.loginSuccess` (`auth_state_provider.dart:46-65`) — 화면에서 명시적으로 `AuthInterceptor.saveToken()` 호출

두 경로가 동시에 동작하므로 같은 토큰을 두 번 씁니다. 기능상 문제는 없으나 책임이 중복돼 있습니다.

### (4) 401이 나면 무슨 일이 벌어지는가 — ✅ **해결됨 (2026-08-21). 초판 서술은 전면 무효**

> ⚠️ **초판(2026-08-20) 서술 `"갱신 없이 삭제만 함"` 은 현재 코드에 대해 완전히 무효입니다.**
> ~~"Refresh Token 으로 재발급하는 코드가 없습니다. 재요청(retry) 코드도 없습니다."~~
> ~~"CLAUDE.md 가 401 자동 갱신을 단언하지만 사실이 아닙니다."~~
> → `auth_interceptor.dart` 가 **표준 refresh 큐 패턴을 전부 구현**했습니다. `CLAUDE.md` 서술이 이제 사실입니다.

```dart
static Future<String?>? _refreshFuture;   // :14

Future<String?> _refreshAccessToken(RequestOptions options) {
  final ongoingRefresh = _refreshFuture;
  if (ongoingRefresh != null) return ongoingRefresh;   // 진행 중이면 그 Future 를 공유
  final refreshFuture = _performRefresh(options).whenComplete(() => _refreshFuture = null);

  return refreshFuture;
}
```

**갱신·재시도 요청의 재귀 방지**: `_createPlainDio()` (`auth_interceptor.dart:188-198`) 로
인터셉터가 없는 별도 Dio 를 만들어 사용하므로 `AuthInterceptor` 를 다시 타지 않습니다.

**P0-1 (비밀번호 오타로 로그아웃) 도 함께 해소**: `/auth/resident/change-password` 나

### (5) 토큰 갱신 호출처 — ✅ **해결됨 (2026-08-21). 초판 서술 무효**

> ⚠️ ~~"`AuthRemoteDataSource.refreshToken()` 의 유일한 호출자는 `checkAutoLogin()` 이며,

### P0-1. 비밀번호 변경·회원 탈퇴 실패(401) 시 로그인 토큰이 삭제됨 → 예기치 않은 로그아웃

> ### ✅ 해결됨 (2026-08-21)
> `AuthInterceptor.onError` 가 401 을 받아도 **즉시 지우지 않고 refresh 를 먼저 시도**하며,
> **갱신에 실패한 경우에만** `_clearToken()` 을 호출합니다.
> - `lib/core/network/interceptors/auth_interceptor.dart:102` — `_refreshAccessToken()` 먼저 시도
> - `lib/core/network/interceptors/auth_interceptor.dart:104-109` — `newAccessToken == null` 일 때만 `_clearToken()`
> - `lib/core/network/interceptors/auth_interceptor.dart:80-85` — 로그인/회원가입 401 은 토큰을 건드리지 않음
>
> 따라서 비밀번호 오타로 인한 401 은 갱신 성공 후 원 요청이 재시도되고, 서버의 "비밀번호 불일치" 응답이
> 그대로 화면에 전달됩니다. 세션은 유지됩니다.
> **잔여**: 갱신 실패로 토큰을 지울 때 `AuthStateNotifier.setUnauthenticated()` 를 함께 호출하지는 않습니다(수정 방향 3번 미적용).

- **증상**: 입주민이 "비밀번호 변경"에서 현재 비밀번호를 한 번만 틀려도, 또는 "회원 탈퇴"에서 비밀번호를 틀려도, 그 순간 access/refresh 토큰이 모두 삭제됨. 화면은 그대로 있어서 사용자는 눈치채지 못하지만, 이후 모든 API가 401로 실패하고 **앱을 껐다 켜면 로그인 화면으로 튕김.**
- **근거**:
  - `lib/core/network/interceptors/auth_interceptor.dart:62-72` — 401이고 path에 `/login`·`/register`가 없으면 `_clearToken()`
  - `lib/modules/resident/data/datasources/resident_auth_remote_datasource.dart:99-107` — `/auth/resident/change-password`가 401/400을 "현재 비밀번호 불일치"로 사용
  - `lib/data/datasources/auth_remote_datasource.dart:221-236` — `DELETE /users/me` 401을 "비밀번호 불일치"로 사용
  - `lib/modules/resident/presentation/screens/change_password_screen.dart:117-127` — 화면은 "현재 비밀번호를 확인해주세요"만 표시하고 재로그인 유도 없음
- **사용자 영향**: **매우 높음.** 가장 흔한 사용자 실수(비밀번호 오타)가 곧바로 세션 상실로 이어짐.
- **수정 방향**:
  1. `AuthInterceptor.onError`에서 토큰 삭제 대상을 화이트리스트 방식으로 좁힌다 — 비밀번호 확인용 401 경로(`/auth/resident/change-password`, `/users/me`)는 제외.
  2. 근본적으로는 백엔드가 "비밀번호 불일치"에 401 대신 400/422를 반환하도록 정렬하는 것이 옳음(백엔드 협의 필요).
  3. 토큰을 지울 때는 `AuthStateNotifier.setUnauthenticated()`도 함께 호출해 앱 상태와 저장소를 일치시킨다.
- **재배포**: 필요

### P0-2. 401 자동 토큰 갱신이 구현되어 있지 않음 (문서는 구현됐다고 기술)

> ### ✅ 해결됨 (2026-08-21)

- **사용자 영향**: **매우 높음.** 토큰 수명이 짧을수록(예: 1시간) 사용 중 세션 끊김이 잦아짐.

- **재배포**: 필요

> (Dio 인터셉터 경계에서는 `DioException` 만 전달 가능하므로 이 부분은 불가피).
> 대신 **`ApiClient` 가 경계에서 언랩**하도록 바뀌어, 상위 계층 계약이 하나로 정리되었습니다.
>
> ```dart
> // lib/core/network/api_client.dart:42-48
> Future<Response<T>> _guard<T>(Future<Response<T>> Function() send) async {
>   try {
>     return await send();
>   } on DioException catch (e) {
>     throw ApiException.from(e);      // DioException 은 여기서 끝난다
>   }
> }
> ```
> ```dart
> // lib/core/network/exceptions/api_exception.dart:24-44
> factory ApiException.from(Object? error) {
>   if (error is ApiException) return error;
>   if (error is DioException) {
>     final inner = error.error;
>     if (inner is ApiException) return inner;   // ErrorInterceptor 가 실어 보낸 인스턴스
>     ...
>   }
>   ...
> }
> ```
>
> **확정된 예외 계약**:
> `ErrorInterceptor` 가 `ApiException` 을 `DioException.error` 에 실음
> → `ApiClient._guard()` 가 언랩
> → **상위(datasource/provider/screen)에는 `ApiException` 만 전파**
> → datasource 는 `on ApiException catch { rethrow }`, 화면은 `showErrorAlert(context, error: e, fallback: ...)`
>
> 초판이 "무력화된다" 고 지목한 코드들은 **전부 정상 동작**합니다
> (`auth_remote_datasource.dart`, `department_remote_datasource.dart`, `user_profile_screen.dart` 등).
> `get`/`post`/`put`/`delete`/`patch` 5개 메서드 모두 `_guard` 를 경유합니다 (`api_client.dart:51-131`).

- **근거**: `core/network/interceptors/error_interceptor.dart:10-18` — `DioException(..., error: apiException, ...)`을 새로 만들어 전달.
  이 때문에 아래 코드가 전부 무력화됩니다:
  - `lib/data/datasources/auth_remote_datasource.dart:38, 69, 96, 121, 146, 173, 195, 246` — `if (e is ApiException) rethrow` 8곳 (항상 false)
  - `lib/data/datasources/auth_remote_datasource.dart:229-243` — `on ApiException` + statusCode 401/404 분기 (데드 코드)
  - `modules/headquarters/data/datasources/department_remote_datasource.dart:50, 70, 108, 156, 210, 230` — 동일 6곳
  - `modules/resident/presentation/screens/user_profile_screen.dart:236` — 동일

  반면 `on DioException catch (e) { ... throw ApiException(...) }` 패턴을 쓰는 DataSource(예: `manager/data/datasources/attendance_remote_datasource.dart:22-43`)는 정상 동작하며, 그 결과 `attendance_provider.dart:109, 135`의 `on ApiException`은 제대로 매칭됩니다. **같은 프로젝트 안에 두 가지 계약이 공존**하는 상태입니다.
- **수정 방향**: `ErrorInterceptor`가 `handler.reject`로 `ApiException`을 그대로 던지도록 통일하거나, 전 DataSource를 `on DioException` 변환 방식으로 통일. 어느 쪽이든 **하나로** 정해야 합니다.
- **재배포**: 필요
