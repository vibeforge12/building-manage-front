# 통합 품질 게이트

Dev Firebase 설정 검사는 `tool/check_dev_environment.sh`에서 실행한다.
iOS Dev 설치 스크립트와 Firebase 선택 스크립트의 문법·환경 제한도 검사한다. 실제 iOS 서명/설치와 APNs 수신은 `IOS_DEVICE_ID=<UDID> make dev-ios` 이후 실기기로 별도 확인한다.
백엔드 단위 테스트에는 dev 키 누락 및 다른 프로젝트 키 차단 검사가 포함된다.
이 검사는 실제 기기의 푸시 수신을 보장하지 않는다. Android 실기기 수신과
iOS APNs 연결·수신은 별도로 확인하며, 미실행 항목은 완료로 간주하지 않는다.

## 실행

프론트 저장소에서 다음 명령 하나를 실행한다.

```bash
make quality
```

결과는 `build/quality-gate/<실행시각>/report.md`에 저장되고, 가장 최근 결과는
`build/quality-gate/latest/report.md`에서 확인할 수 있다. 검사가 하나라도 실패하면 명령도 실패 코드로 끝나므로 CI에서 그대로 사용할 수 있다.

백엔드 검사는 일반 단위 테스트와 별도로 서비스 신청 권한·입력 검증 회귀 테스트를 먼저 실행한다. 정지된 계정 차단, 타 직원 서비스 신청자 접근 차단, 검색어 길이 제한이 깨지면 품질 게이트가 즉시 실패한다.

기본 실행 항목:

서비스 사진·기존 디자인 회귀도 독립 항목으로 실행한다(`test/life_service_images_test.dart`).
최대 5장 선택·삭제, 수정 시 기존 사진 유지·제거, 저장 실패 후 중복 업로드 없는 재시도,
선택 직후 사진 데이터를 확보해 임시 파일이 사라져도 저장하는지, 파일 읽기 실패 시 내부 경로를 노출하지 않는지,
Dev 사진 주소의 API 호스트 연결과 빈 파일 차단을 검사한다.
기존 공고 등록 화면과 서비스 등록·상세를 320/390/768px에서 렌더링하며 320px는 글자 크기 130%를 적용한다.
`DESIGN_CAPTURE=1 flutter test test/life_service_images_test.dart`로 비교 PNG를 `build/design-service/`에 저장할 수 있다.
Mac 캡처는 시스템 한글 폰트를 대체 사용하므로 글꼴의 픽셀 단위 동일성을 보장하는 골든 검사는 아니다.
백엔드 보안 회귀에는 사진 바이트 형식·10MiB 제한·건물 범위·중복/개수·Dev 로컬 저장·서명 변조/만료 차단·운영 로컬 읽기 차단이 포함된다.

1. Flutter 의존성 동기화, 정적 분석, 전체 테스트
2. Android ARM64 릴리스 APK 및 코드 크기 분석
3. 백엔드 의존성 무결성, NestJS 린트, 보안 회귀, 단위 테스트, E2E 테스트, 프로덕션 빌드
4. 프론트·백엔드 `git diff --check`
5. Android 기기가 없으면 첫 번째 AVD를 자동 시작한 뒤 APK 설치, 콜드 스타트 5회, profile 모드 화면 프레임 측정
6. 격리된 로컬 API 50회 반복 요청의 p95 검사
7. 테스트 API 주소가 명시된 경우에만 추가 k6 부하 검사

입주민 홈 재진입 회귀(`test/resident_life_service_section_test.dart`)도 별도 항목으로 실행한다.
홈은 서버 `canApply=true`인 항목만 표시하며 마감·이미 신청·정원 도달·신청 시작 전 항목은 숨긴다.
필터 후 두 항목 미리보기, 마감된 항목만 있을 때에도 전체 목록을 거쳐 상세 진입, 빈 상태·로딩·오류에서 전체보기 유지,
신청/마감 상태 문구, 재시도 및 작은 화면·큰 글꼴을 검증한다.
실제 대시보드 연결 테스트에서는 신청 후 복귀 시 홈 카드가 빠지는지, 상세·전체 목록에서 돌아오면 다시 조회하는지도 검증한다.
알림 스택·새로고침 회귀(`test/notification_navigation_test.dart`, `test/life_service_refresh_test.dart`)도 별도 실행한다.
역할별 홈 복귀, 같은 알림 반복·동시 탭, 계정 변경 시 이동 중단, 신청 목록·상세·내역·명단의 짧은/빈/오류 응답에서 당겨 새로고침, 명단 검색어 유지와 상세 복귀 후 재조회를 검증한다.
만석 수동 마감 회귀(`test/life_service_close_test.dart`)는 서버 `canClose`에 따른 버튼 활성화, 확인 취소·확정, 중복 요청 잠금, 실패 후 재시도, 수동 마감 후 비활성화를 검증한다. 필드가 없는 구버전 서버에서는 권한을 추정하지 않고 비활성화하므로 서버를 먼저 배포한다.
여러 Android가 연결돼 있으면 `QUALITY_ANDROID_DEVICE_ID`로 검사 대상을 명시할 수 있다. 잘못된 기기 ID는 실패로 기록하고 다른 기기로 조용히 바꾸지 않는다. 실사용 계정이 있는 기기에서 profile 테스트를 실행하면 서명 충돌 또는 설치 교체가 발생할 수 있으므로 격리된 에뮬레이터에서 프레임 검사를 수행하고, 실기기 성능은 별도로 확인한다.
실기기에서 마감 알림 없이 홈 → 서비스 신청 전체보기 → 마감 항목 상세로 다시 들어가는 확인은 별도로 수행한다.

Android 빌드에는 실행마다 다른 `DEV_BUILD_REVISION` 값을 전달해 Dart/AOT 빌드 입력을 갱신한다.
빌드 성공·APK 설치 성공만으로 최신 화면 반영을 판정하지 않으며, 설치 파일 대조와 실제 화면 확인은 별도로 수행한다.

운영·공유 서버에 실수로 부하를 주지 않도록 API 부하 검사는 기본적으로 비활성화한다.
대신 기본 실행에서도 실제 HTTP 계층을 거치는 격리 로컬 성능 스모크가 수행된다.

```bash
QUALITY_API_URL=https://test-api.example.com make quality
```

CI처럼 의존성을 처음부터 재설치하려면 다음 환경 변수를 함께 사용한다.

```bash
QUALITY_INSTALL_DEPS=1 make quality
```

## 화면 성능 기준

숫자로 공개된 Google/Flutter 공식 기준을 바탕으로 하며, 토스 기술 블로그에서 강조하는 사용자 체감 경로의 반복 측정과 실제 기기 자동화 원칙을 적용한다.

| 항목 | 품질 게이트 | 근거 |
|---|---:|---|
| 60Hz 프레임 예산 | 16.67ms | Flutter는 60fps에서 약 16ms 이내 렌더링을 권고한다. |
| 느린 프레임 비율 | 1% 이하 | 공식 경계 16ms를 사용한 프로젝트 회귀 방지 기준이다. 1%는 프로젝트 정책이다. |
| 자동 AVD 느린 프레임 비율 | 3% 이하 | 호스트 스케줄링 편차를 포함한 자동 실행 회귀 감시 기준이다. 제품 성능 합격 기준은 아니다. |
| Frozen frame | 700ms 이상 0건 | Android는 700ms 이상을 frozen frame으로 정의하고 없어야 한다고 권고한다. |
| 콜드 스타트 p50 | 500ms 이하 | Google 앱 성능 가이드의 콜드 스타트 목표다. |
| 콜드 스타트 p95 | 1,000ms 이하 | 기기 편차를 감안한 프로젝트 보조 기준이다. |
| 자동 AVD 콜드 스타트 | p50 4,000ms / p95 6,000ms 이하 | 앱 멈춤과 큰 회귀를 감지하는 안전선이다. 제품 성능 합격 기준은 아니다. |
| API 응답 | p95 500ms 이하 | 사용자 체감 화면을 막는 일반 API의 프로젝트 기준이다. |
| API 오류율 | 1% 미만 | 프로젝트 부하 테스트 기준이다. |

공식 자료:

- [Google Android 성능 측정 개요](https://developer.android.com/topic/performance/measuring-performance)
- [Google Android 느린 렌더링과 frozen frame](https://developer.android.com/topic/performance/vitals/render)
- [Flutter 성능 모범 사례](https://docs.flutter.dev/perf/best-practices)
- [Flutter DevTools Performance view](https://docs.flutter.dev/tools/devtools/performance)
- [토스 프론트엔드 서비스 최적화](https://toss.tech/article/32583)
- [토스의 디바이스 팜 만들기](https://toss.tech/article/device-farm-nebula)

토스 공개 자료는 특정 모바일 프레임·시작 시간의 합격 숫자를 공개하지 않는다. 따라서 토스 자료에서 측정 원칙과 실제 기기 자동화 방식을 가져오고, 자동 실패 기준의 숫자는 Google/Flutter 공식 문서와 이 프로젝트의 명시적 보조 기준을 사용한다.

## 측정 범위와 한계

- 프레임 검사는 debug가 아니라 연결된 Android 대상의 profile 모드에서 실행한다. 실기기가 없으면 깨끗한 상태로 부팅한 AVD와 호스트 GPU를 사용한다.
- 현재 자동 시나리오는 앱이 진입한 첫 화면의 스크롤 또는 반복 프레임을 측정한다. 주민·담당자·관리자의 인증 후 핵심 화면은 테스트 계정과 테스트 API가 준비되면 별도 시나리오로 추가해야 한다.
- 콜드 스타트는 ADB `am start -W`의 `TotalTime`을 사용한다. 실기기는 Google 목표인 p50 500ms·p95 1,000ms를 적용한다. 자동 AVD의 p50 4,000ms·p95 6,000ms는 가상화 비용과 호스트 부하를 감안해 앱 멈춤과 큰 회귀만 감지하는 안전선이다. 제품 성능은 반드시 같은 기준 실기기에서 비교한다.
- API 부하 검사는 명시적으로 `QUALITY_API_URL`을 준 경우에만 실행한다.
- 연결 기기가 없으면 `QUALITY_ANDROID_AVD` 또는 첫 번째 AVD를 저장 상태 없이 headless로 자동 시작하고 호스트 GPU를 사용한다. 실행 가능한 기기도 AVD도 없으면 실패 처리한다.
- `QUALITY_API_URL`을 지정했는데 k6가 없으면 실패 처리한다. 외부 주소를 지정하지 않은 기본 실행은 로컬 API 성능 검사로 대체하며 SKIP으로 집계하지 않는다.
